# Bugfix: Post-Supabase Migration Issues

Last updated: 2026-06-21

This document tracks bugs discovered after the Supabase migration and their
fixes. Each scope is committed as a micro commit.

## Scope 1 (P0): Double-toggle bug in score save

**Root cause**: `SummaryModal.trySaveScore` called `onSetGameScore` then
`onTogglePlayedGame` for unplayed games. `setScoreInSnapshot` already
auto-adds to `playedGames`, so the second call toggles it back off — causing a
race condition where two publishes collide on the same version.

**Fix**: Removed the redundant `onTogglePlayedGame` call.

**Files**: `src/components/SummaryModal.tsx`

## Scope 2 (P0): Unresolved player names error not recognized

**Root cause**: `errors.ts` only matched 4 server error phrases. The
"unresolved player names" rejection from `publish_session` fell through to a
generic "Failed to save" message with no indication of which names were
unresolved.

**Fix**: Added pattern matching for "unresolved player" and
"unresolved players" with the raw server detail appended.

**Files**: `src/queries/errors.ts`

## Scope 3 (P0): Cannot insert new player names when creating session

**Root cause**: `publish_session` rejects any player name not registered in
`bm.player_aliases`. Identity registration functions (`ensure_player`,
`register_player_alias`) were service_role-only, so the anon client could not
register new names.

**Fix**:
- New migration `000035`: creates `bm.register_player(p_name, p_canonical_name)`
  — a public-facing wrapper that handles both "add new" and "merge to existing"
  cases. Validates input, idempotent.
- New endpoint `registerPlayer(name, canonicalName?)` in `endpoints.ts`.
- New `ResolvePlayersModal` component: pre-checks local players against
  `list_players` when ShareButton is clicked. For each unknown name, shows a
  popup with "Add as new player" or "Merge with existing player" (dropdown).
- `ShareButton` wiring: resolves all unknown names before publishing.

**Files**: `supabase/migrations/20260618_000035_bm_register_player_rpc.sql`,
`src/queries/endpoints.ts`, `src/components/ResolvePlayersModal.tsx`,
`src/components/ShareButton.tsx`

### Post-fix 1: register_player case bug (migration 000039)

Migration 000035 had two bugs in `register_player`:
1. `normalize_player_name(p_canonical_name)` lowercased the canonical name
   before passing to `ensure_player`. Merge "Freddie" → "Fredi" saved
   "fredi" (lowercase) to `bm.players.canonical_name`.
2. Merge case didn't resolve existing player via alias lookup. Created
   duplicate players (e.g., "fredi" alongside existing "Fredi").

Migration 000039 rewrites `register_player` to preserve original case and
resolve existing players via normalized alias lookup before creating new.

**Files**: `supabase/migrations/20260618_000039_bm_fix_register_player_case.sql`

### Post-fix 2: publish_session v_internal_id NULL for new sessions (migration 000041)

Pre-existing bug since migration 000022. `v_internal_id` is initialized to
`gen_random_uuid()` in the DECLARE block, but `SELECT...INTO v_internal_id`
overwrites it to NULL when the session doesn't exist yet. Subsequent INSERTs
into child tables set `session_internal_id = NULL`, triggering the
`sync_session_identity` trigger error: "session identity is required for
session_courts".

Migration 000041 adds `if not found then v_internal_id := gen_random_uuid()`
after the SELECT block in both `publish_session` and `publish_tournament`.

**Note**: Migration 000041 was necessary but insufficient — see Post-fix 3.

**Files**: `supabase/migrations/20260618_000041_bm_fix_publish_new_session_internal_id.sql`

### Post-fix 3: publish_session `found` flag overwritten by validation CTEs (migration 000042)

Migration 000041 fixed `v_internal_id` but the error persisted. Deep
investigation revealed the **real root cause**: PL/pgSQL's `found` boolean
is reset by every `SELECT...INTO`.

Flow that caused the bug:
1. Session lookup `SELECT...INTO` → `found = false` (new session, correct)
2. `if not found then` → restores `v_id`, `v_share_id`, `v_internal_id` ✓
3. Unresolved players CTE `SELECT...INTO v_unresolved` → `found = true`
   (because resolved players were found)
4. Invalid refs CTE `SELECT...INTO v_invalid_refs` → `found = true`
5. Duplicate canonical CTE `SELECT...INTO v_duplicate_resolution` → `found = true`
6. `if found then` → takes **UPDATE path** for a session that doesn't exist!
7. UPDATE matches 0 rows (session not in DB)
8. INSERT into `session_courts` → trigger can't find session → error

Additionally, `v_id` and `v_share_id` were also NULL (same `SELECT...INTO`
issue as `v_internal_id`).

Fix: capture `found` into a local `v_session_found` boolean immediately after
the session lookup, before any CTE can overwrite it. Also restore `v_id` and
`v_share_id` from `v_lookup` when not found.

The INSERT path (brand new session) was never exercised before because:
- all existing sessions were backfilled from legacy data
- smoke tests only republish existing sessions
- the app only started creating new sessions after the Supabase migration

**Files**: `supabase/migrations/20260621_000042_bm_fix_publish_v_id_null_for_new_sessions.sql`

## Scope 4 (P1): Closure-captured pendingSnapshot in swap hooks

**Root cause**: `useSwapPlayers` and `useSwapTeams` used a closure variable
`pendingSnapshot` shared between `onMutate` and `mutationFn`. Concurrent swaps
on the same hook instance could overwrite the variable before the first
mutationFn reads it.

**Fix**: Removed `pendingSnapshot`. Both hooks now read the optimistically-
updated cache directly in `mutationFn` (same pattern as `useSwapSlots`).

**Files**: `src/queries/sessions.ts`

## Scope 5 (P1): Replace player hits unresolved name rejection

**Root cause**: `useReplacePlayer` publishes a snapshot with the new name. If
the new name is not registered, `publish_session` rejects with "unresolved
player names".

**Fix**: `ReplacePlayerModal` now calls `registerPlayer` before publishing
if the new name is unknown. Reuses the same pre-check logic from Scope 3.

**Files**: `src/components/SummaryModal.tsx`

## Scope 6 (P2): useSwapSlots publish-from-cache clarification

**Root cause**: `useSwapSlots.mutationFn` publishes the optimistic cache
directly instead of re-deriving. This is intentional (double-apply would
revert the swap) but the comment was insufficient.

**Fix**: Expanded the inline comment explaining the invariant and the
narrow race window.

**Files**: `src/queries/sessions.ts`

## Scope 7 (P2): No auto-refetch on version mismatch

**Root cause**: When a mutation hits "version mismatch", the user must
manually reload. The cache is rolled back but the stale version persists.

**Fix**: All session mutation hooks now refetch the session on error before
rolling back, so the cache gets a fresh version. The user can retry
immediately instead of reloading.

**Files**: `src/queries/sessions.ts`

## Scope 8 (P3): SQLSTATE errcodes dropped in migration 000009

**Root cause**: Migration `000009` replaced explicit SQLSTATE codes (`40001`
for serialization_failure, `55P03` for lock_not_available) with bare
`RAISE EXCEPTION` text. Clients cannot reliably distinguish "retry now" from
"reload required".

**Initial fix attempt (000036)**: Restored `USING errcode` clauses on all
concurrency exceptions. Also fixed a jsonb operator bug (`->>ci.court_index`
→ `->ci.court_index` for courtTimes array access).

**PostgREST hang discovered**: Testing revealed that PostgREST (via Supabase
REST API) hangs when `publish_session` raises an exception with `USING errcode`
on the version-mismatch path. This is the same issue migration `000009` fixed
by removing the errcodes. The hang does not occur when calling the function
directly via SQL Editor — only via PostgREST REST transport.

**Final fix (000037)**: Re-applied both functions identically to 000036 but
without the `USING errcode` clauses. Client-side `RpcError` class and errcode
matching in `errors.ts` remain as harmless fallback (never triggered, falls
back to message text matching). When Supabase upgrades PostgREST and the hang
is resolved, errcodes can be re-introduced via a new migration.

**Files**: `supabase/migrations/20260618_000036_bm_restore_errcodes.sql`,
`supabase/migrations/20260618_000037_bm_drop_errcodes_for_postgrest_compat.sql`,
`src/queries/endpoints.ts`, `src/queries/errors.ts`

## Scope 9 (Medium): Missing advisory lock in publish_session

**Root cause**: `publish_tournament` uses `pg_try_advisory_xact_lock` for
global mutual exclusion before the row-level `FOR UPDATE NOWAIT`.
`publish_session` only uses `FOR UPDATE NOWAIT`, which doesn't protect the
INSERT path for new sessions (no row to lock). Two concurrent requests for
the same new session ID can both pass the row lock and one will get a raw
PostgreSQL unique constraint violation (500 error) instead of the friendly
"is being updated" message.

**Fix**: Added `pg_try_advisory_xact_lock` to `publish_session`, matching
the pattern already used in `publish_tournament`.

**Files**: `supabase/migrations/20260621_000043_bm_publish_session_advisory_lock.sql`

## Scope 10 (High): Missing cancelQueries in toggle/score mutations

**Root cause**: `useTogglePlayed` and `useSetScore` did not call
`cancelQueries` in their `onMutate`. All other mutation hooks
(`useSwapPlayers`, `useSwapTeams`, `useSetAbsent`, `useReplacePlayer`,
`useSwapSlots`) correctly cancel in-flight queries before applying the
optimistic update.

Without `cancelQueries`, a background refetch (e.g., from
`refetchOnWindowFocus`) can complete after `onMutate` sets the optimistic
state, silently overwriting the optimistic update. Then `mutationFn` reads
the overwritten cache (without the user's change) and publishes stale data
to the server. The user's toggle/score is silently lost.

**Why the original `cancelQueries` caused flicker**: The flicker was a
3-layer problem:
1. `onSettled` invalidated the session query → fixed in commit `1b2dbd2`
2. `cancelQueries` raced with background refetch → fixed by removing it
3. `mutationFn` re-applied snapshot function → fixed in commit `8d1d98b`

After all 3 layers were fixed, `cancelQueries` alone (without `onSettled`
session invalidation) is safe. The swap hooks prove this pattern works —
they all have `cancelQueries` + `onSettled` (without session invalidation)
and do not flicker.

**Fix**: Restored `cancelQueries` to `useTogglePlayed` and `useSetScore`
`onMutate` callbacks.

**Files**: `src/queries/sessions.ts`

## Scope 11 (Medium): Missing version mismatch refetch in usePublishSession

**Root cause**: `usePublishSession` had no `onError` handler. When a version
mismatch occurs during publish from GeneratePage, the user sees an error
toast but the cache is not refetched. The cache retains the stale version.
If the user retries, the same version mismatch occurs (because the cache
still has the old version). The user is stuck until a refetch happens (e.g.,
window focus).

By contrast, all SharedSessionPage mutations use `refetchOnVersionMismatch`
which refetches on version mismatch.

**Fix**: Added `onError` handler to `usePublishSession` that refetches the
session on version mismatch, allowing the user to retry immediately.

**Files**: `src/queries/sessions.ts`

### PostgREST hang note

Migration 000036 introduced `USING errcode` clauses that cause PostgREST to
hang on the version-mismatch path. Migration 000037 reverts the errcodes.
If `publish_session` hangs via REST API but works in SQL Editor, apply
000037 (or verify it has been applied).
